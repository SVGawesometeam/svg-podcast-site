# Как мы работаем с расшифровками на marinamogilko.co

Документ описывает фактический процесс, который сложился в репозитории `svg-podcast-site`:
откуда берётся расшифровка, кто главный при расхождениях, что руками, что скриптом, что
записывается в протокол. Последний раздел — переносимые правила, если алгоритм нужно
приложить к другой задаче.

---

## 0. Из чего состоит система

```
podcast-video-ids.txt   → список того, что вообще существует на сайте (111 ID)
API бэкенда (Railway)   → черновик страницы: мета + расшифровка
Trint CSV               → настоящая диаризация (кто говорит), внешний источник
build.js                → рендерит HTML, главную, sitemap.xml, llms.txt
public/                 → то, что деплоится; ручные правки живут прямо здесь
transcript-fixes/*.json → протокол правок: что исправили, на каком основании
Vercel                  → деплой по push в main
```

Ключевые файлы и константы — в начале [build.js](build.js):

- `API_BASE` = `https://svg-dashboard-production.up.railway.app/api/podcast-page`
- `IDS_FILE` = `podcast-video-ids.txt`
- `PUBLIC_DIR` = `public/`
- `FIXES_DIR` = `transcript-fixes/`

Что отдаёт API на `GET /api/podcast-page/<videoId>`: `title`, `guestName`, `guestTitle`,
`publishedAt`, `duration`, `thumbnail`, `episodeSummary`, `keyTakeaways[]`, `timestamps[]`,
`relatedVideos[]` и `transcript` — одна строка markdown в формате `**Имя:** текст`,
абзацы разделены пустой строкой.

Нужен Node 18+ (в коде используется глобальный `fetch`).

## 1. Главный принцип: сборка инкрементальная

В `build()` (см. [build.js:160](build.js:160)) есть строчка, которая определяет весь рабочий процесс:

> если `public/episode/<id>/index.html` уже существует — эпизод **пропускается**.

Из готовой страницы билд вычитывает только мету для главной и sitemap
(`readExistingEpisodeMeta`), сам HTML не трогает. Следствия:

1. Любая ручная правка страницы переживает сколько угодно прогонов `node build.js`.
2. Чтобы пересобрать страницу с нуля, её нужно **сначала удалить**. Иначе ничего не произойдёт.
3. Удаление страницы = потеря всех ручных правок. Поэтому существует `transcript-fixes/`.

## 2. Новый выпуск — по шагам

**Шаг 1. Взять videoId.** Это 11 символов из ссылки YouTube: `youtube.com/watch?v=<videoId>`.
Он же — URL страницы: `/episode/<videoId>/`.

**Шаг 2. Дописать ID в `podcast-video-ids.txt`** — одна строка, без пустых строк вокруг.
Этот файл — единственный список того, что существует на сайте. Нет ID в файле — нет страницы,
нет её в sitemap и в llms.txt.

**Шаг 3. Собрать.**

```bash
node build.js
```

Что происходит: по каждому ID из списка — если страницы нет, идёт запрос в API, рендерится
`public/episode/<id>/index.html`; затем всегда перерисовываются `public/index.html`,
`public/sitemap.xml` и секция гостей в `public/llms.txt`. В конце печатается
`Built / Skipped / Failed / Total` — на новом выпуске должно быть `Built: 1`, `Failed: 0`.

**Шаг 4. Проверить страницу глазами** — чек-лист в разделе 10. На этом шаге решается главное:
расшифровка от бэкенда пригодна как есть или выпуск идёт на пересборку из Trint (раздел 4).

**Шаг 5. Внести правки** — прямо в `public/episode/<id>/index.html` — и записать протокол в
`transcript-fixes/<id>.json`.

**Шаг 6. Закоммитить и запушить** — Vercel деплоит из `main` автоматически.

## 3. Иерархия источников: кому верим при расхождении

1. **Видео и Марина.** Высшая инстанция, спор закрыт.
2. **Trint CSV** — истина о том, **кто** говорит. Диаризация считается из аудио, а не угадывается.
3. **Текст страницы** — истина о том, **что** сказано. Он уже вычищен руками (Claude, Anthropic,
   ChatGPT, названия компаний) и читается лучше сырого Trint. Поэтому при пересборке Trint решает
   только атрибуцию, слова остаются наши.
4. **Бэкенд** — черновик. Исторически он просил модель угадать говорящего по субтитрам YouTube,
   в которых информации о говорящих нет вообще. Это источник почти всех ошибок атрибуции на сайте:
   вопросы ведущей были подписаны гостем, встречались фантомные спикеры (на выпуске Эрика
   Бриньольфссона — «Reed Hoffman», имя из примера в промпте форматирования).

**Правило, купленное ошибкой:** логика разговора не заменяет данные диаризации. На выпуске
Бриньольфссона реплика «There's nothing like that anymore» шла сразу после вопроса ведущей и
выглядела как сбой разметки — предложение отдать её гостю Марина отклонила, это действительно
её слова. Trint был прав, рассуждение — нет. Такие случаи записываются в протокол полем
`falseCorrectionAvoided`, чтобы их не «исправили» повторно.

## 4. Пересборка атрибуции из Trint — по шагам

Применяется, когда бэкенд отдал кашу: спикеров нет вовсе, они съехали по всему выпуску или
появился человек, которого в записи не было.

**4.1. Экспорт.** Марина выгружает из Trint CSV с говорящими (сегменты с таймкодами).

**4.2. Correspondence check — файл соответствует опубликованному монтажу.** Проверяется по
**первым строкам**, а не по длительности: финальный монтаж бывает короче видео, потому что
концовка и музыка речи не содержат (у Гэри Вайнерчука расхождение 112 секунд при полном
совпадении текста). Совпадение по секундам — приятный бонус, не критерий. Дополнительно
смотрится покрытие речи и отсутствие сплошных пропусков — если Trint снят не с того монтажа,
это видно сразу.

**4.3. Карта спикеров с доказательством на каждого.** `Speaker N → имя`, и рядом — почему:
кто открывает выпуск («Welcome to Silicon Valley Girl»), кто задаёт вопросы (32 вопроса из
57 реплик), кто читает призыв подписаться на рассылку, кто говорит «when I teach at Stanford».
Доказательство должно быть проверяемым по тексту, а не «по ощущению».

**4.4. Артефакты диаризации.** Спикер с двумя репликами по три слова («Yeah.», «Oh, yeah.»),
целиком лежащими внутри блоков другого спикера, — это бэкчэннел ведущей, а не человек. Клеим
к владельцу и записываем, что склеили.

**4.5. Выравнивание.** Абзацы страницы сопоставляются с сегментами Trint цепочками из четырёх
слов, которые голосуют за позицию абзаца. Абзац, внутри которого меняется голос, режется по
границе.

**4.6. Второй проход — фразы-маркеры.** Ищем то, что может сказать только один человек:
«my documentary», «my newsletter», «welcome to Silicon Valley Girl». Каждое место, где
диаризация с этим спорит, попадает в отчёт и разбирается руками. На выпуске Мо Гавдата таких
конфликтов было семь, настоящих — два (остальные: Гэри назвал Марину «a Silicon Valley girl»,
Фей-Фей упомянула своих студентов).

**4.7. Односложные реакции.** «Yeah», «Exactly», у которых нет собственного сегмента в Trint,
раздаются по чередованию — и это фиксируется как допущение, а не как факт (на одной пересборке
таких было 26).

**4.8. Форматирование под чтение и цитирование.** Сегменты Trint склеиваются по говорящему в
реплики; длинные монологи режутся на абзацы **до ~170 слов** по границам предложений; ярлык
спикера ставится **только на первом абзаце реплики**, продолжения идут без ярлыка. Абзацев
длиннее ~2500 знаков быть не должно — из такой стены текста никакая поисковая или AI-выдача
не процитирует. Попутно снимаются висячие кавычки — типовой артефакт распознавания
(17–19 штук на выпуск).

**4.9. Протокол.** Пишется `transcript-fixes/<videoId>.json` (раздел 5).

**4.10. Публикация правки.** Либо правка HTML на месте, либо честная пересборка:

```bash
rm -rf public/episode/<videoId>
```

```bash
node build.js
```

Второй путь имеет смысл только если исправлен сам бэкенд — иначе билд принесёт ту же кашу.

## 5. `transcript-fixes/<videoId>.json` — что это и что туда писать

**Важно понимать статус файла: сегодня это протокол, а не конфиг.** В `build.js` есть готовые
функции `loadFix`, `applyTranscriptFix` (splits / assignments / speakerRenames) и
`assertKnownSpeakers` — [build.js:15–116](build.js:15) — но они **ни откуда не вызываются**, и
ни один из 14 существующих JSON-файлов не содержит полей `splits` / `assignments` /
`speakerRenames`. Фактические правки лежат в отрендеренном HTML, а JSON отвечает на вопрос
«что здесь чинили и на каком основании». Заготовка автопатча ждёт, когда её подключат к `build()`
(см. раздел 11).

Поля, которые сложились по факту:

| Поле | Что в нём |
|---|---|
| `videoId`, `episode` | что за выпуск |
| `transcriptSource` | откуда взята расшифровка (имя CSV, trintId) |
| `note` | что было сломано и почему пересобирали |
| `trintSpeakerMap` | `Speaker N → настоящее имя` |
| `speakerMapEvidence` | доказательство по каждому спикеру + `confirmedBy` (кто и когда подтвердил) |
| `correspondenceCheck` | чем доказано, что файл — от опубликованного монтажа |
| `crossCheck` | независимая сверка (например, ручная сверка Марины) |
| `falseCorrectionAvoided` | правка, которая выглядела очевидной и оказалась неверной |
| `formatting` | сколько реплик, во сколько абзацев, как резали |
| `adsKept` / `adsRemoved` | что сделали с рекламой и что при этом сохранили |
| `textFixes` / `fixes` | точечные замены («Liverman» → «Liberman», «23 and me» → «23andMe») |
| `title` | было / стало / зачем |
| `jsonLd` | если правили структурированные данные вручную |
| `backendIssue` | дефект бэкенда, который надо чинить в другом репозитории |

Правило записи одно: **каждое утверждение — с внешне проверяемым основанием, догадка помечается
как догадка** (`unresolvedNote`, `marinaConfirmed`, «присвоено по контексту соседнего клипа»).

## 6. Компиляции (нарезки из разных выпусков)

Бэкенд на них не распознаёт спикеров и подписывает всех «a special guest». Процедура:

1. Текст каждого клипа сверяется с корпусом уже опубликованных расшифровок одиночных выпусков
   по **6-граммам**. Порог подтверждения — **≥5 совпадений**: имя присваивается тому выпуску, где
   текст клипа лежит дословно. Это внешне проверяемый факт, а не догадка.
2. Очень короткие клипы (2–15 слов) присваиваются по контексту соседнего подтверждённого клипа
   того же гостя — и это отмечается в протоколе.
3. Если совпадения нет вовсе (расшифровки клипа и полного выпуска сделаны независимыми прогонами
   ASR и расходятся по словам) — только просмотр видео Мариной, с пометкой `marinaConfirmed`.
4. Вопросы ведущей, ошибочно помеченные гостем, возвращаются Марине.
5. В конце в протоколе фиксируется `unresolvedSpecialGuestLabels` — сколько ярлыков осталось
   неопознанными. Цель — 0.

**Имена гостей в заголовок компиляции не ставим.** У каждого из них есть своя страница; имя в
заголовке нарезки сталкивает две страницы сайта в одном запросе «[имя] podcast», и компиляция —
худший ответ (гость там говорит около полутора минут). Имена остаются там, где они работают:
`guest-name`, meta description, JSON-LD `performer`, ярлыки спикеров.

## 7. Реклама

- Автоматически: `renderEpisodePage` вырезает блоки по шаблонам «This part of the video is
  brought to you by…», «This episode is sponsored by…», «This video is sponsored by…» до
  следующего ярлыка спикера или фразы возврата («Now let's get back…»).
- Вручную при пересборке решение принимается штучно и записывается: у братьев Либерман вырезаны
  спонсорский блок MongoDB Atlas (220 слов) и призыв подписаться на рассылку (34 слова), причём
  вопрос ведущей в конце того же блока сохранён — на него отвечает следующая реплика. У
  Бриньольфссона и Джурветсона реклама оставлена.
- **Общее правило пока не утверждено.** Это известный долг: договориться и выровнять все страницы
  одним проходом.

## 8. Заголовки — house style

Формат: **роль и компания впереди, имя после вертикальной черты.**

```
Duolingo CEO: … | Luis von Ahn
Khan Academy CEO: … | Sal Khan
Gonka Founders on Who Controls AI Wealth in 3 Years | The Liberman Brothers
```

Зачем: fanout-запросы идут по двум формулам — «[Имя] podcast/interview» и «[Компания] CEO
podcast». Эталон — страница Ryan Roslansky, единственная, которая закрывает обе сразу, и с самым
высоким citation rate на сайте (2.0 против 0.31 у главной).

Правила:

- Роль берётся из `guestTitle` эпизода, **не выдумывается**.
- Оба сооснователя остаются в заголовке — каждое имя это отдельный запрос, выкинув одно, мы его теряем.
- Одно имя — одно написание по всей странице. У Гэри Вайнерчука было три варианта («Gary
  Vaynerchuk», «Gary», «Gary Vee») на 74 ярлыка — это размывает сигнал, который мы как раз
  хотим сконцентрировать.
- Правка заголовка тянет за собой карточки related на других страницах и строку на главной.

## 9. Что ещё делает `build.js` (не забыть при правках)

- **Главная** — перерисовывается всегда, из всех эпизодов, отсортированных по дате.
- **sitemap.xml с честным `lastmod`.** Дата меняется только когда реально изменился контент
  страницы: считается sha1 отрендеренного HTML и сравнивается с `sitemap-lastmod.json`. Страница,
  которую видим впервые, датируется днём публикации выпуска, а не сегодняшним, — чтобы один
  прогон не объявил Google, что изменились все 111 страниц.
- **llms.txt** — перегенерируется **только** секция `## Podcast Guests and Their Episodes`,
  остальной текст файла написан руками и не трогается. Из индекса выпадают соло-выпуски
  (`guestName === "Marina Mogilko"`) и компиляции (несколько имён через запятую).
- **Соло-выпуски.** Пустой `guestName` от бэкенда рендерился как заглушка «Special Guest»;
  теперь такой выпуск подписывается как Marina Mogilko / «Host, Silicon Valley Girl Podcast»,
  а первый абзац расшифровки получает её ярлык.
- **Двойное экранирование.** Всё, что билд вычитывает обратно из готовых страниц, уже
  экранировано, а шаблоны экранируют ещё раз — для этого есть `unesc()`. Без него заголовок
  «ChatGPT & Codex» на каждом прогоне обрастает лишним `&amp;`.

## 10. Чек-лист перед публикацией страницы

- [ ] `node build.js` отработал без `Failed`.
- [ ] Ярлыки спикеров: только реальные участники записи, никаких «Guest», «Speaker 2»,
      «a special guest», ни одного человека, которого в записи нет.
- [ ] Вопросы ведущей подписаны Мариной, ответы — гостем; нет абзацев, где вопрос приклеен к
      концу чужого ответа.
- [ ] Одно написание имени на всю страницу.
- [ ] Нет абзацев-стен (>2500 знаков), длинные монологи разбиты.
- [ ] Имена людей, компаний и продуктов не перевраны распознаванием (типовые: Claude → «cloud»,
      ChatGPT → «Chad JPT», Sam Altman → «Chuck Alman»).
- [ ] Заголовок в house style, роль из `guestTitle`.
- [ ] Meta description и og/twitter description заполнены, без «a special guest, ,».
- [ ] JSON-LD: `performer`, `datePublished`, `associatedMedia` на месте.
- [ ] Внизу есть блок related (страница без него — сирота, на неё ничего не ведёт), заголовки
      карточек прочитаны с целевых страниц, а не написаны по памяти.
- [ ] Расшифровка соответствует опубликованному монтажу, а не черновику.
- [ ] `transcript-fixes/<id>.json` записан, если что-то чинили.

## 11. Деплой

```bash
git add -A && git commit -m "..."
```

```bash
git push origin main
```

Vercel собирает из `main` автоматически, статика раздаётся из `public/`. Редиректы старых URL
(`/podcast/*`, `/ru/*`, `/yt_channel`) живут в [vercel.json](vercel.json).

**Что сейчас не доделано** (полезно знать тому, кто продолжит):

- Машинерия автоприменения фиксов в `build.js` написана, но не подключена к `build()`.
  Пока правки существуют только в отрендеренном HTML.
- Правило по рекламе не унифицировано.
- Корневая причина ошибок атрибуции — в бэкенде `svg-dashboard` (другой репозиторий): пайплайн
  назначает спикеров моделью по субтитрам YouTube, где данных о говорящих нет.
- Вспомогательные скрипты в корне (`batch-build.js`, `fix-transcripts.js`, `fix-guests.js`,
  `generate-podcast-page.js`, `patch-jsonld.js`) — разовые инструменты прошлых проходов, в
  текущем процессе не используются. `fix-transcripts.js` требует `ANTHROPIC_API_KEY`.

## 12. Как переложить этот алгоритм на свою задачу

Девять правил, которые в этом проекте работают и не зависят от подкастов:

1. **Один список — источник правды о том, что существует.** У нас это `podcast-video-ids.txt`.
   Не в списке — не существует нигде: ни в сборке, ни в sitemap, ни в индексе.

2. **Сборка инкрементальная и идемпотентная.** Готовое не перезаписывается; пересборка — это
   осознанное удаление, отдельным действием. Иначе ручная работа будет молча затираться
   автоматикой, и ей перестанут пользоваться.

3. **Иерархия источников записана заранее, до первого спора.** Кто прав про «кто», кто прав про
   «что», кто черновик, кто высшая инстанция. Разные источники бывают правы про разные поля
   одной записи: у нас Trint решает атрибуцию, но не слова.

4. **Автоматика предлагает — человек подтверждает.** Подтверждение фиксируется с именем и датой
   (`confirmedBy: "Марина, 2026-07-22"`), иначе через месяц никто не вспомнит, что именно было
   проверено глазами, а что сгенерировано.

5. **Каждый факт — с проверяемым основанием, догадка помечена как догадка.** «Speaker 2 — это
   ведущая, потому что задаёт 32 вопроса из 57 и читает призыв подписаться» — основание.
   «Похоже, это она» — нет.

6. **Соответствие источника результату проверяется явно и правильным способом.** Мы проверяем
   Trint-файл по первым строкам, а не по длительности, потому что длительность врёт на
   смонтированных концовках. В своей задаче найдите такой же признак — устойчивый, а не удобный.

7. **Протокол правок лежит рядом с данными.** Не в чате, не в голове, не только в коммите:
   отдельный файл на единицу контента, который отвечает «что чинили, чем доказали». Он же —
   инструкция по восстановлению, если запись пересоберут с нуля.

8. **Отменённые «исправления» записываются наравне с принятыми.** Правка, которая выглядела
   очевидной и оказалась неверной, вернётся через полгода в чьём-то новом проходе — если её
   отмену не записать.

9. **Ломайте сборку, а не продакшн.** Неизвестный ярлык спикера должен ронять билд с внятным
   сообщением («добавьте настоящее имя в `transcript-fixes/<id>.json` после проверки видео»), а
   не тихо уезжать на сайт. Валидацию пишите одновременно с генератором.

И десятое, специфичное, но переносимое: **формат подчиняется потребителю.** Абзацы до 170 слов и
ярлык только на первом абзаце реплики — не эстетика, а следствие того, что страницу цитируют
кусками. Сначала решите, кто и как будет читать результат, потом форматируйте.
